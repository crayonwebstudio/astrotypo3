Startup defect found by a real browser test and fixed (20 Oct 2026): the deployed builder failed to start with the banner "Builder failed to start: Storage.addType is not a function", an empty blocks panel and a blank canvas. Root cause: the builder registered its storage with `editor.Storage.addType(...)`, a method that does not exist on the GrapesJS 0.23.8 StorageManager (custom storages register with `StorageManager.add(type, storage)`, see the StorageManager class in `grapesjs/dist/index.d.ts`; `addType` belongs to DomComponents, TraitManager, AssetManager and StyleManager). The pure-logic tests never init a real editor, so they could not catch an editor API mismatch. Fix: registration moved into the shared, exported `registerGrapesStorage()` in `src/lib/typo3Storage.mjs`, which calls `editor.Storage.add('typo3-api', ...)`; `builder.astro` calls that single function. Regression test `tests/storage-editor.test.mjs` inits the real grapesjs package in jsdom through the same code path and asserts the storage type is registered, all 15 registry blocks reach the BlockManager, and `editor.store()` serializes to page JSON and POSTs to the save endpoint. The error was reproduced in that harness before the fix and is gone after it; the built bundle now contains the `Storage.add(...)` registration and no `addType('typo3-api'` call. Honest limits: saving from the browser UI was not click-tested by automated browser tooling; Style Manager edits are canvas only, not part of the content contract; array and object props are edited as JSON text in traits. |
