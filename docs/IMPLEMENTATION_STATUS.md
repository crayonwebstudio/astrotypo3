Root cause: the builder passed raw CSS text in `canvas: { styles: [cssText] }`, but GrapesJS 0.23.8 `CanvasConfig.styles` entries are stylesheet URLs that become `<link>` tags in the canvas iframe head, so the browser tried to fetch the CSS text as a URL and got nothing. Fix: the app now serves a dedicated canvas stylesheet at the stable path `/builder-canvas.css` (endpoint `src/pages/builder-canvas.css.ts`, composed by `src/lib/canvasCss.mjs` from the same `tokens.css` and `global.css` sources the public site uses, so tokens and the `.hero`, `.grid`, `.card`, `.site-header` rules match the published rendering), and the builder passes the absolute URL of that path to `canvas.styles`. Second, the toolbar showed "Unsaved changes" immediately after the initial page load, before any edit. The first fix (`markClean()` also calling `editor.clearDirtyCount()`) did NOT hold: a further real browser re-test still showed the indicator on load, and still after merely selecting the hero. True root cause, verified in the installed grapesjs 0.23.8 source (`dist/grapes.mjs`, `EditorModel.handleUpdates`): GrapesJS counts changes asynchronously, every change is debounced into a `setTimeout(..., 0)` that increments `changesCount`, while `clearDirtyCount()` resets the counter synchronously. The synchronous reset in `markClean()` ran in the same microtask chain as the load, before the load's own pending increment, which landed one macrotask later, set the counter to 1, and triggered the `update` event that re-showed the label. Selection itself never dirties the editor in 0.23.8 (it never calls `changesUp`); it only revealed the already positive counter. Fix: dirty tracking moved to `src/lib/dirtyTracking.mjs` (`createDirtyTracker`). The label is gated while the builder initializes, and the clean state is established only after the counter has settled (stable across consecutive macrotask reads), via `finishInitialization()`, which the bootstrap awaits after ALL async init steps (element types fetched and registered into the live registry, page loaded through the API client, final `setComponents` done). The Load page and Save draft handlers use the same settling reset (`settleAndMarkClean()`), because a load's `setComponents` and the last edit before a save can also leave a pending increment. Real edits after initialization still mark the page dirty. Regression coverage: `tests/dirty-tracking.test.mjs` (6 tests) reproduces the mechanism against a fake editor that mirrors the verified dist semantics (debounced increment, synchronous clear), including a control case showing a plain synchronous clear being overwritten by the pending increment. The real editor's event order could not be reproduced under jsdom (timers starve once components render there, observed during this fix), so the mechanism was verified in the dist source and the behaviour in the real browser re-tests. Editing failures follow-up (27 Oct 2026): the browser re-test after the deploy above found toolbar Undo/Redo doing nothing and invalid JSON wiping the feature-grid cards live. Undo root cause was granularity, not the button path: live applies made every keystroke its own undo entry, and Backbone.Undo only groups same-callstack actions, so in a real browser (one task per keystroke) three Undo clicks reverted three keystrokes and the edit stayed, while the jsdom harness typed in one synchronous task and one click reverted everything. Fix in src/lib/liveTraits.mjs: an edit session (first input until change/blur or deselect) collapses to one undo entry on commit (per-keystroke tail entries removed, one entry added via a silent restore to the pre-edit value followed by a full apply; collapse only when the tail is clean). Invalid JSON root cause: live applies had no validation, so invalid text applied at once and attributesToProps fell back to [] on render. Fix: array/object props are validated as JSON before applying; invalid text never touches the attribute, the field is marked (aria-invalid, red border, message as title) and the error is reported to the status line naming the field, valid text applies and clears (the page restores the ready status only when the status currently shows a JSON error).
